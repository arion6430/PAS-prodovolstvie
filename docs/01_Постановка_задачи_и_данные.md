| Пункт | Формулировка |

| Прогнозируемый показатель | Средняя потребительская цена, руб/кг, по 8–10 позициям «борщевого набора» и фруктов (картофель, капуста, лук, морковь, огурцы, помидоры, яблоки, бананы и др.) в разрезе *РФ / ЦФО / Москва*, горизонт — 1–3 месяца |

**Разнородность выполнена с запасом:** форматы SDMX-XML, обычный XML, HTML и JSON; частоты месяц и день; разные поставщики (Росстат, ЦБ, метеосервис).

### Объём выгруженных образцов

* Розничные цены: 10 товаров × 4 территории, 276–284 месяца на ряд. Дубликатов и пустых значений нет, пропусков месяцев внутри рядов нет. «Помидоры свежие» начинаются только с 2007 г.
* Цены производителей: 7 товаров × 3 территории, до 116 месяцев на ряд. **Есть пропуски** (например, «Лук репчатый» по ЦФО — 38 точек из 116; вероятно, данные скрыты по требованиям конфиденциальности).
* Курсы: около 6,6 тыс. дней. Ключевая ставка: около 3,3 тыс. записей. Погода: около 9,8 тыс. дней на регион, без пропусков.

## 3. Особенности данных (основа для профильных компонентов)

Найденные особенности источников помогают набрать баллы по критериям «обработка данных» и «компоненты по выбору».

1. **Смена справочника территорий с 2023 г.** Ряд «Российская Федерация» заканчивается в 12.2022, с 01.2023 он продолжается под новым кодом «РФ без учёта новых субъектов» (`643` → `643004.АГ`). Разрыва в уровнях на стыке нет: в 12.2022 картофель стоил 31,9 руб/кг, в 01.2023 — 33,9 руб/кг. Нужен справочник территорий с периодами действия (SCD2) и правило «склейки» → это закрывает **историзацию и ведение справочников**.
2. **Смена кодов ОКПД2 в ценах производителей.** «Огурцы» до 2023 г. идут под кодом `01.13.32`, с 2024 г. — под кодом `01.13.32.000`, то же с томатами. Это две записи с одинаковым названием → нужны **разрешение сущностей и дедупликация** (единый мастер-справочник продуктов).
3. **Разные названия одного товара в источниках.** В рознице «Картофель, кг», у производителей «Картофель» (ОКПД2 `01.13.51`), в рознице «Капуста белокочанная свежая», у производителей «Капуста всех сортов» → таблица соответствия продуктов (**мастер-данные**).
4. **Разные единицы измерения.** Розница в руб/кг, производители в руб/т → нормализация в слое очистки.
5. **Накопленные периоды.** В показателе 57693 кроме месяцев есть периоды «январь-февраль» … «январь-декабрь». Их нужно отфильтровывать (это правило контроля качества).
6. **Пересмотр данных (ревизии).** ЕМИСС иногда уточняет опубликованные значения → храним версии значений (историзация факта) и пишем в журнал загрузок, что изменилось.
7. **Разная частота.** Курсы и погода дневные, цены месячные → агрегация к месяцу на уровне витрины.
8. **Числа в формате «25,79»** (запятая как десятичный разделитель) → проверка соответствия типов.

## 4. Концепция системы

```
 Источники                Загрузка (инкрементальная, журнал)        Слои хранения                       Аналитика
┌───────────────┐        ┌──────────────────────────────┐   ┌──────────────────────────┐   ┌───────────────────────┐
│ ЕМИСС 31448   │──SDMX─▶│                              │   │ raw     — сырые ответы   │   │ Модели прогноза:      │
│ ЕМИСС 57693   │──SDMX─▶│  extractors + retry/timeout  │──▶│           (файлы, как есть)│   │  • сезонный наивный   │
│ ЦБ: курсы     │──XML──▶│  load_log, watermark по дате │   │ staging — разобранные    │   │    (базовая модель)   │
│ ЦБ: ставка    │──HTML─▶│  идемпотентный upsert        │   │           таблицы + DQ   │   │  • SARIMA / ETS       │
│ Open-Meteo    │──JSON─▶│                              │   │ core    — справочники    │──▶│  • градиентный бустинг│
└───────────────┘        └──────────────────────────────┘   │           (SCD2) + факты │   │    с лагами и экзоген.│
                                                            │ mart    — витрины        │   ├───────────────────────┤
                         Контроль качества (DQ) ──────────▶ │           (месяц×товар×  │   │ Дашборды:             │
                         Метаданные / lineage ────────────▶ │            регион)       │──▶│  • предметный         │
                                                            └──────────────────────────┘   │  • операционный       │
                                                                                           └───────────────────────┘
```

### Выбранный стек
* **PostgreSQL 16 в Docker** — хранилище со схемами `raw / staging / core / marts / meta / snapshots`; там же отдельные базы метаданных Airflow и Superset. Настоящая СУБД с транзакциями и ролями: Superset подключается под ролью только для чтения витрин.
* **Python** — загрузчики источников (`requests`, `pandas`, `psycopg`), журнал загрузок, миграции схемы raw/meta.
* **dbt (dbt-postgres)** — преобразования staging → core → marts, снимки SCD2 (историзация), тесты качества данных, автодокументация и граф lineage.
* **Apache Airflow 3** — оркестрация: ежедневное расписание, параллельная загрузка источников, повторы, история запусков.
* **Apache Superset** — предметный и операционный дашборды поверх витрин.
* **statsmodels / LightGBM** — модели прогноза (этап 11-й недели).
* Весь стенд поднимается одной командой `docker compose up -d --build`.

### Модели (минимум две + базовая)
* Базовая модель: **сезонный наивный прогноз** (значение того же месяца прошлого года × годовая динамика).
* **SARIMA/ETS** по каждому ряду.
* **LightGBM** на лагах цены, ценах производителей (лаг 1–2 мес.), курсе USD, погодных аномалиях вегетационного сезона.
* Валидация: скользящее окно по времени (expanding window, без перемешивания), метрики MAPE и MAE. Утечки контролируем так: в признаки берём только данные, опубликованные до даты прогноза.

### Дашборды
* **Предметный** (для аналитика закупок): каждый элемент отвечает на свой вопрос.
  * «Что подорожает в ближайшие 3 месяца?» — прогноз с доверительным интервалом.
  * «Где цена сейчас аномальна относительно сезона?» — отклонение от сезонной нормы.
  * «Какова наценка между полем и прилавком?» — сравнение цены производителя и розничной цены.
  * Фильтры: товар, регион, период.
* **Операционный** (для владельца системы): журнал загрузок, свежесть каждого источника, результаты DQ-проверок, ошибки и повторы, качество моделей во времени.

### Профильные компоненты (30 баллов) — все три естественно вытекают из данных
1. **Контроль качества.** Проверки полноты (пропуски месяцев), уникальности (ключ товар×регион×месяц), допустимости и диапазонов (цена > 0, скачок за месяц не больше ×3), типов (запятая/точка), ссылочной целостности (код ОКАТО/ОКПД2 есть в справочнике), актуальности (последний месяц не старше 60 дней). Результаты сохраняются в таблицу `dq_results`, плохие строки уходят в карантин.
2. **Метаданные и lineage.** Цепочка «дашборд → витрина → core → staging → raw-файл → URL источника». Её даёт `dbt docs` (граф моделей от источника до витрины), дополнительно — журнал `meta.load_log` и ссылка каждой строки raw на сырой файл.
3. **Историзация.** SCD2 для справочников территорий и продуктов (на реальных сменах кодов 2023–2024 гг.) плюс версии фактов при ревизиях Росстата.

## 5. Риски и ограничения

| Риск | Что делаем |
|---|---|
| У fedstat.ru нет официального API, механизм выгрузки взят из кода страницы (токен + POST-форма) | Повторы с паузой, таймауты, сохранение сырого ответа. Если структура страницы изменится, понятная ошибка попадёт в журнал |
| Месячные данные приходят примерно с 3–6-недельной задержкой | Прогноз строим «от последнего опубликованного месяца», свежесть показываем в операционном дашборде |
| Пропуски в ценах производителей | Используем их как признак с флагом пропуска, контролируем полноту в DQ |
| rosstat.gov.ru недоступен из текущей сети | Не критично: всё нужное берётся из ЕМИСС |
